# Segurança

## Como relatar uma falha

Não abra issue pública para falha de segurança. Use o relato privado do GitHub: aba **Security**, botão **Report a vulnerability** neste repositório.

Inclua a versão (`rastro --version`), o passo a passo para reproduzir e o impacto que você enxerga. A resposta inicial vem em até 7 dias.

## O que o Rastro promete

- **Só na sua máquina:** a API escuta em `127.0.0.1` e recusa `Host` que não seja a própria máquina.
- **Pedido de outro site:** POST, PUT, PATCH e DELETE com `Origin` de fora são recusados.
- **Disco:** só lê as pastas cadastradas; caminho absoluto e `..` vindos da requisição são recusados.
- **Processos:** o build e os testes da validação rodam sem shell, com argumentos separados, tempo limite e o comando que está na configuração do repositório, nunca o que vem da requisição que dispara a validação. O comando se edita nas Configurações ([ADR-008](docs/adr/adr-008-comandos-pela-tela.md)), com a mesma proteção de `Origin` e `AllowedHosts`: um site aberto no navegador não consegue trocá-lo.
- **Janela própria** ([ADR-007](docs/adr/adr-007-janela-propria.md)): o `rastro` abre uma janela nativa (Photino.NET) com o WebView do sistema (WebView2 no Windows, WebKit no macOS e no Linux), apontando só para a API local. A página fala com a janela por uma mensagem de formato fixo, conferida dos dois lados: a única aceita pede a caixa "Escolher pasta", e a resposta é o caminho que o usuário escolheu (ou nada, se cancelou). Nenhuma mensagem executa comando, lê disco ou chama a API; o cadastro do repositório continua passando pelas regras da API. Se faltar o WebView2, o Rastro avisa e segue no navegador, sem baixar nada. O cache do WebView fica em `~/.rastro/janela`, e as ferramentas de desenvolvedor da janela ficam desligadas.
- **Chave de API dos provedores de IA:** fica cifrada no banco local e nunca volta na resposta nem no log.
- **IA:** só envia ao provedor o trecho de código necessário, e só quando você liga o modo provedor. Na pergunta livre sobre o fluxo, vão a pergunta, o mapa do fluxo (nomes de métodos e `arquivo:linha`), as regras e até 8 trechos de código em volta das entradas e das decisões. A pergunta e o código vão marcados como dado, e a IA é instruída a ignorar instruções dentro deles. Na sugestão de melhora de uma consulta (botão "Sugerir melhora com a IA" da aba "Analisar consulta"), vão a consulta como foi colada (inclusive os literais), os achados sem IA e só as tabelas que ela usa (nomes, colunas, tipos, nulo, chaves e índices), também marcados como dado; nunca a string de conexão, os dados das tabelas nem o resto do esquema. A resposta passa pela conferência do núcleo (leitor de SQL do dialeto do repositório e esquema) antes de aparecer, e nada é aplicado nem executado: quem copia é o usuário. O texto da consulta não vai para o log.
- **Banco de dados** ([ADR-006](docs/adr/adr-006-visao-do-banco.md)): o esquema sai do código do repositório. A conexão com um banco vivo (SQL Server ou PostgreSQL, cadastrada por repositório na tela do banco) é opcional e só de leitura: o Rastro **nunca lê dados das tabelas**, só o catálogo (tabelas, colunas, chaves, índices, views e procedures) e o plano estimado de uma consulta, sem executá-la. As consultas ao catálogo são fixas no código, e a consulta do plano passa antes pelo leitor de SQL do dialeto (uma instrução só, sem `SET`, `EXEC` nem DDL; no PostgreSQL, também sem `COPY`, `CALL`, `DO`, `SELECT INTO` e sem função de efeito colateral conhecida, como `pg_sleep`, `set_config`, `nextval` e `dblink`). No PostgreSQL, o plano é o `EXPLAIN` sem `ANALYZE`, nunca o `EXPLAIN ANALYZE`, dentro de uma transação só de leitura que sempre volta atrás, numa conexão aberta com `default_transaction_read_only` ligado e o `statement_timeout` do próprio banco, num comando de um lote só (o PostgreSQL recusa duas instruções nele). A string de conexão fica cifrada no banco local, como a chave da IA, e nunca volta na resposta, no log nem para a IA. Os comandos têm tempo limite e a conexão não entra em pool (o `SHOWPLAN_XML` e o `PREPARE` nunca passam para outra conexão). Recomendamos um usuário de banco com permissão mínima: no SQL Server, `VIEW DEFINITION` basta para o catálogo; o plano estimado pede também `SHOWPLAN` e o `SELECT` nas tabelas da consulta, porque o SQL Server só mostra o plano a quem pode rodar a instrução. No PostgreSQL, `CONNECT` no banco basta para o catálogo; o plano pede o `USAGE` no schema e o `SELECT` nas tabelas da consulta, e recomendamos `ALTER ROLE usuario SET default_transaction_read_only = on`. O Rastro não usa esse `SELECT` para ler dado nenhum: a garantia é o código acima, e a permissão mínima é a segunda camada. A análise de consulta (aba "Analisar consulta", `analyze_query` no MCP) só lê o texto pelo leitor de SQL do dialeto (T-SQL pelo ScriptDom, PostgreSQL pelo SqlParserCS, os dois em código gerenciado, dentro do processo): a consulta não é executada, não vai a banco nenhum e o texto dela não vai para o log. Com banco vivo, o catálogo também traz a estimativa de linhas de cada tabela (estatística do catálogo, nunca contagem nem dado). O MCP (`get_query_plan` e o custo no `propose_query_rewrite`) usa a mesma porta do leitor de SQL e a mesma conexão cadastrada na tela: lê as chaves de cifra do banco local só para abrir a conexão, nunca cria nem grava chave, e a string nunca vai para o agente, para a resposta nem para o log.

Uma falha em qualquer um desses pontos é um relato bem-vindo.
