## How to report a vulnerability

Do not open a public issue for a security flaw. Use GitHub's private reporting: the **Security** tab, then the **Report a vulnerability** button in this repository.

Include the version (`rastro --version`), the steps to reproduce, and the impact you see. You get a first reply within 7 days.

## What Rastro promises

- **Only on your machine:** the API listens on `127.0.0.1` and rejects any `Host` that is not the machine itself.
- **Requests from other sites:** POST, PUT, PATCH and DELETE with a foreign `Origin` are rejected.
- **Language:** the route that saves the language (`PUT api/settings/language`) only writes `Rastro:Language` to `config.json`, accepts only the three known values, and has the same `Origin` and `AllowedHosts` protection as the other routes that change data.
- **Disk:** it only reads registered folders; absolute paths and `..` coming from the request are rejected.
- **Processes:** the build and tests of a validation run without a shell, with separate arguments, a timeout, and the command stored in the repository configuration, never one that comes from the request that triggers the validation. The command is edited in Settings ([ADR-008](docs/adr/adr-008-comandos-pela-tela.md)), with the same `Origin` and `AllowedHosts` protection: a site open in your browser cannot change it.
- **Own window** ([ADR-007](docs/adr/adr-007-janela-propria.md)): `rastro` opens a native window (Photino.NET) with the system WebView (WebView2 on Windows, WebKit on macOS and Linux), pointing only at the local API. The page talks to the window through a fixed-format message, checked on both sides: the only one accepted asks for the "Choose folder" dialog, and the reply is the path the user chose (or nothing, if they canceled). No message runs a command, reads the disk, or calls the API; repository registration still goes through the API rules. If WebView2 is missing, Rastro warns you and keeps running in the browser, without downloading anything. The WebView cache lives in `~/.rastro/janela`, and the window's developer tools are turned off.
- **AI provider API keys:** stored encrypted in the local database and never returned in a response or written to a log.
- **AI:** it only sends the provider the code excerpt that is needed, and only when you turn on provider mode. For a free-form question about a flow, it sends the question, the flow map (method names and `file:line`), the rules, and up to 8 code excerpts around the entry points and decisions. The question and the code are marked as data, and the AI is instructed to ignore instructions inside them. For a query improvement suggestion (the "Suggest an improvement with AI" button on the "Analyze query" tab), it sends the query as pasted (including literals), the findings produced without AI, and only the tables the query uses (names, columns, types, nullability, keys and indexes), also marked as data; never the connection string, the table data, or the rest of the schema. The reply goes through the core's checks (the SQL reader for the repository's dialect, and the schema) before it is shown, and nothing is applied or executed: the user is the one who copies. The query text is not written to the log.
- **Database** ([ADR-006](docs/adr/adr-006-visao-do-banco.md)): the schema comes from the repository code. The connection to a live database (SQL Server or PostgreSQL, registered per repository on the database screen) is optional and read-only: Rastro **never reads table data**, only the catalog (tables, columns, keys, indexes, views and procedures) and the estimated plan of a query, without running it. The catalog queries are fixed in the code, and the plan query first goes through the SQL reader for the dialect (a single statement, with no `SET`, `EXEC` or DDL; on PostgreSQL, also no `COPY`, `CALL`, `DO`, `SELECT INTO`, and no known side-effect function such as `pg_sleep`, `set_config`, `nextval` and `dblink`). On PostgreSQL, the plan is `EXPLAIN` without `ANALYZE`, never `EXPLAIN ANALYZE`, inside a read-only transaction that is always rolled back, on a connection opened with `default_transaction_read_only` on and the database's own `statement_timeout`, in a single-statement batch command (PostgreSQL rejects two statements in it). The connection string is stored encrypted in the local database, like the AI key, and is never returned in a response, written to a log, or sent to the AI. Commands have a timeout and the connection is not pooled (`SHOWPLAN_XML` and `PREPARE` never leak to another connection). We recommend a database user with minimal permissions: on SQL Server, `VIEW DEFINITION` is enough for the catalog; the estimated plan also needs `SHOWPLAN` and `SELECT` on the tables in the query, because SQL Server only shows the plan to someone who can run the statement. On PostgreSQL, `CONNECT` on the database is enough for the catalog; the plan needs `USAGE` on the schema and `SELECT` on the tables in the query, and we recommend `ALTER ROLE usuario SET default_transaction_read_only = on`. Rastro does not use that `SELECT` to read any data: the guarantee is the code described above, and minimal permission is the second layer. Query analysis (the "Analyze query" tab, `analyze_query` in the MCP) only reads the text through the SQL reader for the dialect (T-SQL through ScriptDom, PostgreSQL through SqlParserCS, both managed code, inside the process): the query is not executed, does not go to any database, and its text is not written to the log. With a live database, the catalog also brings each table's row estimate (a catalog statistic, never a count or data). The MCP (`get_query_plan` and the cost in `propose_query_rewrite`) uses the same SQL reader gate and the same connection registered on the screen: it reads the encryption keys from the local database only to open the connection, never creates or writes a key, and the string never goes to the agent, the response, or the log.

A flaw in any of these points is a welcome report.
